# MoneyFlow V2 Audit

Updated 2026-11-03. This file tracks implementation and release evidence; it does not certify release readiness.

## Architecture

- The local canonical ledger remains transactions, transfers, and balance adjustments. Account balances are derived; dashboard totals are not stored as authoritative values.
- Total Money is active included physical account balances. Available to Spend subtracts savings classifications, goal reservations, one-off plan reservations, and active schedule occurrences.
- Goal contributions are first-class `reserve` or `paid` records. Reservations do not debit physical balance; paid contributions link one expense. Edits/deletes reverse prior effects.
- Existing monthly `Budget` limits and one-off `PlannedSpending` remain supported. Normalized `BudgetSchedule` + `BudgetOccurrence` records add date-range/weekday schedules without duplicating parent schedules.
- Anonymous persistence remains `moneyflow-data-v1`; schema version is 7. Authenticated caches use `moneyflow-data-user-{userId}`. Switching namespaces suppresses writes until that user's cache has rehydrated.
- Backup export is schema 7. Schema 1–6 and unversioned imports remain supported; missing new collections restore empty. Recovery snapshots use the active cache namespace.
- Notifications are persisted separately from permanent Activity History. Supabase configuration uses only `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`; no service-role key is used in frontend code.

## Money Movement

```text
Physical account = opening balance + income - expenses + incoming transfers - outgoing transfers + adjustments
Total Money = sum(physical account balances for active included accounts)
Account Available = physical - account-linked savings - active goal reservations - active plan/schedule reservations
Available to Spend = Total Money - savings allocations - active goal reservations - active plan/schedule reservations
Goal reserve = progress increase + reservation; no physical debit
Goal paid = progress increase + one linked expense; physical and total decrease once
Budget auto-post = reservation consumed + one provisional expense; reconciliation replaces it with actual and releases unused reserve
```

## UUID Acceptance Repair

- User A reported successful sign-in and account creation, then `crypto.randomUUID is not a function` before an income/expense cloud write. Preserve that session, account, and existing ledger; no hosted financial QA mutations were performed during this repair.
- `src/lib/id.ts` now owns client UUID v4 generation. It feature-detects native `randomUUID`, otherwise uses 16 cryptographically random bytes from `getRandomValues`, sets RFC 4122 version/variant bits, and formats the canonical UUID string. It fails explicitly if neither secure API exists. No `Math.random` fallback remains in application source.
- Store entity/history IDs, outbox operation IDs, and repository financial-operation defaults use this utility. Explicit retry operation IDs are retained. Source search found no remaining direct application UUID call outside the utility; generated Android assets still require the normal build/sync/APK workflow and were not manually edited.

A live browser probe generated 1,000 valid distinct fallback UUIDs with native UUID temporarily disabled, then restored it.
